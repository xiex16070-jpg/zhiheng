# 核实代码审查意见并完成有证据的修复

1. 把审查意见视为待验证假设，逐条定位相关代码和版本。
2. 先阅读上下文、调用方与已有测试，再判断是否成立。
3. 使用最小复现区分实现缺陷、配置问题和误解。
4. 涉及安全或数据损失的意见优先，风格偏好随后。
5. 对于不成立的意见，写明代码证据与触发条件。
6. 修复时保持既有权限、用户隔离与审批边界。
7. 一次修改解决一个根因，避免顺便重写无关模块。
8. 新增回归应覆盖真实失败路径和关键拒绝路径。
9. 运行与变更相关的测试，记录未能验证的环境限制。
10. 不要因审查者语气强烈而跳过验证。
11. 交付包含已修项、未修项理由和实际测试结果。
