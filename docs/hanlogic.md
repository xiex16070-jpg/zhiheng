# 知衡 HanLogic 0.1

知衡是一门可执行的中文逻辑规则语言。它用于把给定事实、规则、必要条件和例外写成可检查的程序，并输出逐步证明。它不是通用编程语言，也不是自然语言理解器、完整一阶逻辑定理证明器或 Lean/Rocq 的替代品。

核心约定是：**证明只相对于给定程序成立**。来源编号、引文匹配与规则可执行，均不能单独证明自然语言前提真实，或证明把文献翻译成关系时没有误解。Agent 的来源绑定层与此语言的形式执行层分别负责这些检查。

## 运行

```sh
node scripts/hanlogic.mjs examples/hanlogic/program-verification.han
node scripts/hanlogic.mjs examples/hanlogic/evidence-conflicts.han --json
node scripts/hanlogic.mjs examples/hanlogic/exceptions.han --json
```

使用 `-` 作为文件名可从标准输入读取。`--json` 返回结构化事实、查询和证明；语法、安全性或资源错误退出码为 1，错误中含行、列和稳定错误码。命令行仅读取指定程序，不运行程序中声明的文件、网络或系统操作。

## 在工作台选择求解算法

右上角的 **知衡推演** 打开工作台。默认的 **文献推理** 使用对话模型查阅材料。切到 **规则验算**，选择示例、编辑程序并点击 **运行推演**，可以在本地查看每个查询的正反证据、规则行号、候选事实匹配次数和派生事实数。**用于后续对话** 会将当前算法保存为聊天中知衡工具的默认选择。通过 API 调用时可在 `POST /api/logic/evaluate` 请求中同时传入 `program` 和 `algorithm`。

| 算法 | 适用问题 | 本项目的实现 |
| --- | --- | --- |
| 分层正向 `naive`（默认） | 小程序、教学、核对全部派生事实 | 从输入事实出发，在每一层重复应用规则，直到该层没有新增事实。 |
| 半朴素增量 `semi-naive` | 路径闭包、反复递归、需要全量结果的程序分析 | 记录相邻两轮的新增事实。每次连接至少使用一条新增前提，按最左新增位置分开处理含多个递归前提的规则。 |
| 查询导向 `magic-sets` | 只问少数具体对象 | 从每个查询及其反面建立需求表。规则头已绑定的值和左侧前提得到的值向后续前提传播，限制目标层生成的元组。下层先完整求值，确保“除非”检查到已推导的例外；没有查询时计算全量闭包。 |

三种策略共享语法、安全检查、四值查询和证明生成。选择“递归路径 · 比较算法”并分别运行，可比较同一道查询的实际匹配次数。查询导向保留输入事实、下层推导与目标查询需要的推导，结果中的 `factScope` 会标为 `query`。多条证明都成立时，各算法可能先找到不同的证明。超出资源限额会明确报告失败。

实现参考了 Abiteboul 对朴素定点与半朴素递归算法的讲义。Soufflé 在其 Datalog 编译器中也使用半朴素求值。[作者讲义](https://abiteboul.com/TEACHING/DBCOURSE/deductive-eval-datalog.pdf) · [Soufflé 实现说明](https://souffle-lang.org/docs/home/)

查询导向采用 Bancilhon、Maier、Sagiv 和 Ullman 的 Magic Sets 思路。本项目用运行时需求表记录绑定，按规则体从左向右传递。查询的正、反两侧同时播种，并在完整的低层结果上判定默认例外。[原论文](https://doi.org/10.1145/6012.15399) · [Soufflé 的变换规则](https://souffle-lang.github.io/magicset)

## 基本语法

```text
事实 已验证(排序甲) 依据 "source-1"。
事实 满足前置条件(排序甲) 依据 "source-2"。

规则 验证契约：
  若 已验证(?程序) 且 满足前置条件(?程序)
  则 满足后置条件(?程序)
  依据 "source-rule"。

查询 满足后置条件(排序甲)。
```

上面的来源只是语法示例，需要调用方绑定实际检索原文。省略 `依据` 表示给定假设，运行结果会明确提示；不会伪造来源。

- 语句以 `事实`、`规则` 或 `查询` 开头，以 `。`、`;` 或 `；` 结束。文件最后一条允许省略终止符。换行不自动结束语句。
- 关键字与相邻名称之间使用空格。中文并不意味着任意自然语言都能直接执行，例如 `若已验证排序甲则安全` 不属于本语法。
- 关系格式为 `名称(参数，参数)`，支持全角括号和逗号，也支持空参数命题 `已经结束()`。同一关系的参数数量必须一致。
- 不带引号的中文或英文名称是字符串常量；`"排序甲"`、`“排序甲”`、`「排序甲」` 也是字符串。带空格、标点或关键字的常量须加引号。
- 数值常量仅支持 JavaScript 安全整数，且不包含小数点；字符串 `"2"` 与整数 `2` 不同。小数和超大整数必须使用带引号的字符串，从而避免浮点舍入合并不同事实。本版不提供算术运算。
- 变量写作 `?程序` 或 `？程序`。事实与查询必须给出常量；本版不支持带变量的查询枚举。
- `#` 或 `//` 在字符串外引入行注释。
- 来源写作 `依据 "ref-1"、"ref-2"`。来源编号区分大小写，空来源不合法；来源仅为元数据，不能在程序里执行。

简化语法：

```text
程序  := 语句*
语句  := "事实" 原子 [依据] 终止符
       | "规则" 名称 "：" 规则体 [例外] [依据] 终止符
       | "查询" 原子 终止符
规则体 := "若" 条件 "则" 原子
        | "只有" 原子 "才" 原子
条件  := 合取 ("或" 合取)*
合取  := 因子 ("且" 因子)*
因子  := 原子 | "(" 条件 ")"
原子  := ["非"] 关系名 "(" [参数 ("," 参数)*] ")"
例外  := "除非" 原子 ("或" 原子)*
依据  := "依据" 来源编号 ("," 来源编号)*
```

`且` 的优先级高于 `或`；`或` 是包含式或。规则结论必须为单个原子，需要多个结论时写多条规则。嵌套函数、存在量词结论、任意 JavaScript、导入、文件和网络操作均不支持。

## 中文条件方向

```text
规则 充分条件：若 已验证(?程序) 则 可接受(?程序)。
规则 必要条件：只有 获得许可(?程序) 才 已执行(?程序)。
```

第一条只允许从 `已验证` 推到 `可接受`，不允许反过来；第二条表示“获得许可”是“已执行”的必要条件，故从 `已执行` 推到 `获得许可`。它不保证获得许可就已经执行。

没有声明的逆命题或逆否命题不会被自动补入。规则中的全体变量受有限事实域约束；结论及例外中的每个变量，必须在每个 `或` 分支的已声明条件中出现，否则拒绝运行。显式否定的事实条件也可以提供变量绑定。

## 四种查询状态

`非` 是**显式否定**，需要事实或规则支持。没有找到 `P(甲)` 不会产生 `非 P(甲)`。

| 查询的支持 | 反向支持 | 返回状态 | 中文标签 |
| --- | --- | --- | --- |
| 有 | 无 | `true` | 成立 |
| 无 | 有 | `false` | 不成立 |
| 有 | 有 | `both` | 冲突 |
| 无 | 无 | `unknown` | 未知 |

“成立”和“不成立”均指相对于输入程序的支持状态；例如查询 `非 P(甲)` 时，正向支持是 `非 P(甲)`，反向支持是 `P(甲)`。

正负事实独立保存。冲突不会覆盖其中一方，也不会使无关命题全部成立。如果程序显式提供了一条以冲突双方为条件的规则，它仍可按那条给定规则执行。本版采用正负支持对的查询分类，不声称实现完整 Belnap–Dunn 逻辑的所有联结词或蕴涵系统。

## 有边界的例外

```text
事实 已测试(程序甲)。
事实 已测试(程序乙)。
事实 失败样例(程序乙)。

规则 候选：若 已测试(?程序) 则 待进一步验证(?程序) 除非 有反例(?程序)。
规则 反例：若 失败样例(?程序) 则 有反例(?程序)。

查询 待进一步验证(程序甲)。
查询 待进一步验证(程序乙)。
查询 非 有反例(程序甲)。
```

程序甲是候选，程序乙不是已导出的候选，而“程序甲没有反例”仍是未知。即使反例规则写在候选规则后面，也会先完成较低层的反例推导，再判断例外。

`除非 E` 指**当前有限程序的较低层没有导出 E**。它属于明确声明的缺省假设，不是对现实世界的否定证明。多个 `或` 连接的例外只要一个成立，就阻止该规则；若例外同时有正负支持，正向支持仍会阻止规则。

引擎按带正负符号的关系依赖分层，普通条件允许同层递归，例外必须依赖更低层。通过普通规则或显式否定绕出的例外循环也会报 `unstratified_negation`，而不是根据书写顺序随意选一个结果。添加新事实后须重新运行整个程序，旧的缺省结论不会跨运行持久化。

## 证明与确定性

执行器使用有限的前向链闭包，按输入顺序选择第一条可用证明。事实通过关系、正负号、有类型参数去重；重复规则循环在不产生新事实时停止。证明节点只引用已经存在的前提节点，构成无环图，避免递归展开成无限证明树。

一个结论可能存在多种证明，本版只保存第一条，不声称已枚举全部证据路径。修改规则书写顺序可能改变所展示的第一条证明，但在相同完备运行中，分层规则的事实闭包和查询状态保持一致。

每个证明节点包含：

```json
{
  "id": "p3",
  "kind": "rule",
  "conclusion": "满足后置条件(排序甲)",
  "rule": "验证契约",
  "line": 4,
  "refs": ["source-rule"],
  "premises": ["p1", "p2"],
  "assumptions": []
}
```

`refs` 是该语句自己的来源编号，前提来源应沿 `premises` 遍历。使用例外的节点会包含 `assumptions: [{kind: "not-derived", literal: "有反例(程序甲)", scope: "current-program"}]`。`line` 始终指事实或规则声明的起始行，方便来源绑定与编辑器定位。

## 模块接口

```js
import { parseProgram, runProgram, HanLogicError } from '../src/logic/hanlogic.mjs';

const ast = parseProgram(source);
const result = runProgram(source, {
  allowedRefs: new Set(['source-1', 'source-2', 'source-rule']),
  requireEvidence: true,
  limits: { maxSteps: 50000 },
});
```

`parseProgram` 同时进行语法、变量安全、参数数量和例外分层检查。返回 `facts`、`rules`、`queries`，事实通过 `atom` 表示，规则有 `body`、`head`、`unless`、`refs`、`line`；原子为 `{type:'atom',predicate,args:[{kind:'constant'|'variable',value}],negated,line,column}`。

`runProgram` 只接受源码，避免外部直接提供 AST 绕过校验。它返回：

- `status: 'complete'`：仅在整个闭包和结果构造完成后出现。
- `facts`：输入与推导事实，每条含 `id`、`predicate`、`arguments`、`negated`、`text`、`proof`。
- `queries`：查询文本、行号、四种状态及 `positiveProof` / `negativeProof` 节点编号；缺少支持为 `null`。
- `proofs`：共享证明节点；`warnings`：假设、例外和语义映射的限制；`stats`：事实数、规则数、步骤等。

`allowedRefs` 只验证编号是否在调用方提供的白名单内；`requireEvidence` 只要求每条事实和规则声明来源。它们都不检验文献是否蕴涵该语句，这必须由来源绑定和语义审查另外完成。

## 资源边界

默认值同时是硬上限，调用方只能收紧：源文本 50,000 字符，12,000 个词法单元，2,048 条输入或推导事实，128 条规则，64 个查询，关系最多 8 个参数，100,000 个匹配步骤，4,096 个证明节点，条件嵌套 48 层，全程序展开最多 128 个规则分支，每分支最多 24 个原子，单常量 512 字符，500 毫秒墙钟预算。

同一预算覆盖词法、解析、分支展开、依赖分层、推理与结果构造；超限抛 `limit_exceeded`，不会把不完整推导标成“未知”或“成立”。HTTP / Agent 接入层还应在独立 worker 中执行并设外层超时，防止主事件循环被未来实现回归拖住。CLI 会在解码前限制输入字节数。

## 语义参考与边界

安全变量、无函数符号的 Horn 规则与前向链设计参考 [W3C RIF-Core](https://www.w3.org/TR/rif-core/)。本项目自定中文语法、显式否定支持对、分层例外、证明表示与资源限制，**不宣称符合 RIF-Core 的完整交换格式或类型系统**。

规则语言负责演绎，不把归纳、类比或因果外推自动升级为形式证明。有关真实程序的安全性质，需要将准确的程序语义和证明义务提供给相应验证器；在这里声明 `已验证(程序甲)` 本身只是一个输入事实。
